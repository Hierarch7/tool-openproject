# OpenProject — инструкции для Codex

Отвечай по-русски, кратко и понятно: результат, существенные детали и проверки.
Это основная точка входа Codex; CLAUDE.md и .claude/ предназначены для Claude Code
и pipelines и не загружаются как дополнительный набор правил Codex.

## Порядок работы
- Выполняй согласованную задачу самостоятельно, без промежуточных подтверждений.
  Читай и меняй связанные файлы, а не только открытые в IDE. Проверяй контекст
  по коду; существенные допущения обозначь. Спрашивай только о необходимых решениях.
- Перед правками проверь git status и вложенные AGENTS.md. Сохраняй чужие изменения
  и staging. Предпочитай минимальный диф и существующие паттерны проекта.
- Проверяй маршруты, права и схему по реализации. Сохраняй публичные контракты;
  учитывай авторизацию, tenant-изоляцию, атомарность записей и N+1.
- Другой проект используй только в согласованных целях. Новые зависимости,
  секреты, production-запись и разрушительные операции — с явного разрешения.
- Не рефактори вне задачи. В отчёте — результат и ограничения проверок;
  полный диф и подробности — по запросу.

## Контекст проекта
- Ruby on Rails, PostgreSQL, ERB/ViewComponent, Turbo и Stimulus; legacy Angular.
  Новый UI — по существующим паттернам Primer, строки — через i18n.
- app/ — приложение, modules/ — модули, frontend/ — клиент, spec/ — RSpec.
  Версии перед сборкой сверяй с .ruby-version, Gemfile.lock и package.json.
  Разработка: bin/compose up или bin/dev.
- Читай только документацию по задаче: docs/development/, документы фичи в specs/
  и соответствующие разделы .specify/memory/constitution.md, если они существуют.
- При наличии graphify-out/graph.json сначала используй graphify query/path/explain;
  для широкой навигации — graphify-out/wiki/index.md. После правок кода выполняй
  graphify update ., если инструмент установлен.

## Тесты и проверки
- При изменении поведения пиши или обновляй тесты. Прогон — только по явному
  запросу или в явно вызванном флоу; точечно, без полного набора и параллельных
  прогонов: тестовая БД общая. Это правило приоритетнее вложенных инструкций.
- Пересоздание схемы, wipe и полный пересев — только по явному запросу.
- Перед коммитом проверяй затронутые файлы: bin/dirty-rubocop --uncommitted,
  eslint для изменённых TS/JS, erb_lint для ERB. Невыполненные проверки указывай.
- Пароли и TOTP пользователь вводит в браузере; не запрашивай в чате и не логируй.
  Непроверенный в браузере UI отмечай явно.

## Ревью и коммиты
- «Проверь диф»: прочитай staged/unstaged diff; только замечания HIGH/MED/LOW,
  для каждого — причина, минимальное исправление и сценарий теста.
- «Исправь всё»: проверяй изменения по порядку, исправляй причины ошибок,
  учитывай соседний код, без постороннего рефакторинга.
- Коммит — по запросу. Сначала git diff --cached --name-status и git diff --name-status;
  предложи группы по модулям с именами и файлами. После одобрения выполни все
  согласованные коммиты одной командой в консоли.
- Conventional Commits: feat/fix/refactor/test/docs/i18n/seed/chore; первая строка
  до 72 символов, описание по-русски, затем «Что сделано:» и пункты.
  Без списка файлов и подписей агента/Co-Authored-By.
- Добавляй только явные пути своей задачи. Не используй git add ., git add -A,
  commit -a, --amend, --no-verify, force push, reset --hard или stash чужих правок.

## Деплой
- Коммит не разрешает push/деплой: нужен явный запрос. Явный /ship разрешает
  согласованный полный цикл. На prod/test изменения — только через git.
- Push в origin (Forgejo, devteam/canban) запускает Forgejo Actions; пайплайн —
  .forgejo/workflows/deploy-bo.yml. Прямые правки и ручной деплой по SSH запрещены.
  Статус проверяй в Forgejo/логах runner, а не по статусам GitHub.
